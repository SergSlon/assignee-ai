### HIGH (should fix before merge)

- **Docstring lies about PriceClass behavior; selected rate is non-deterministic across edge regions** (`pricing-enricher.ts:717–727`, `pricing-enricher.ts:636–640`). The docstring on `enrichCloudFrontGroup` and the `buildMinimalDesiredState` switch both claim "PriceClass_All (conservative-high estimate that matches the worst-case AWS bill)." Two facts contradict this:
  1. `cloudFrontDistributionPricingDecomposer.decompose()` IGNORES its `_desiredState` parameter (see `packages/core/src/pricing/decomposers/cloudfront-distribution.ts:37`). The PriceClass value in `buildMinimalDesiredState` is dead code — it never reaches the MCP filter set.
  2. The decomposer's only filter is `productFamily=Data Transfer` (no `fromLocation` constraint). The real `AmazonCloudFront` Pricing API returns ~10 entries under `productFamily=Data Transfer` (NA $0.085/GB, EU $0.085, ME/SA $0.110, JP/AU $0.114, SG/KR/TW/HK/PH $0.120, IN $0.109 etc.). `extractTieredPrice` iterates `candidates` and returns the FIRST `isTieredResponse` match (mcp-parser.ts:212–224). Selection order is whatever the MCP server happens to return — not deterministic, not "worst-case."

  Real impact: For a typical Assignee-deployed distribution (the included `static-website.ts` / `cloudfront-distribution-spa-website.ts` / `cloudfront-distribution-static-site.ts` patterns ALL hard-code `PriceClass: "PriceClass_100"`, which only serves NA+EU edges at $0.085/GB), the F6 $/mo label is either correct ($0.085 picked) or overstated by **40%** ($0.120 picked) — depending on which edge-region row the MCP server returned first. Two consecutive runs may show different $/mo for the same distribution.

  Fix (pick one):
  - **(preferred)** Add a `transferType + fromLocation` filter to the data-transfer line item, so the decomposer always pulls the "CloudFront Outbound + North America" rate ladder. Document the choice as "lowest-tier edge region" and rename the docstring to "minimum-edge-rate estimate."
  - **(acceptable interim)** Iterate `candidates` and pick the entry whose `attributes.fromLocation` matches a hard-coded list (e.g. "North America" or whatever maps to the bulk of Assignee deployments). Document the choice.
  - **(weakest fallback)** Iterate all matching items, compute each ladder's bytes cost, and return `max(...)` — that would actually make the docstring's "worst-case" claim true. Note this is non-trivial because each item has its own tier boundaries.

- **`/10K reqs` display label is mathematically wrong in the rate-hint fallback** (`pricing-enricher.ts:820–841`, `cloudfront-distribution.ts:69`, `kms-key.ts:77`, `ssm.ts:86`, `secretsmanager.ts:55`). All four `PER_10K_REQS` decomposers emit `priceUnit: "/10K reqs"` with NO `scale` field. `extractFirstTierPrice(data, "/10K reqs", scale=undefined→1)` returns `$0.0000010000/10K reqs` for the canonical $0.01/10K rate — the number is per-1-request but labeled per-10K. Production code happens to work because the F6 promotion path immediately strips the suffix back off (line 837) to re-extract the raw rate, then multiplies by raw `requests`. But:
  - The rate-hint fallback display string IS user-visible, mislabeled, and **off by 4 orders of magnitude** in implied meaning (claims $0.000001 per 10K reqs ≈ free, real rate is $0.000001 per 1 req).
  - This is pre-existing for all four consumers (KMS, SSM, SecretsManager, CloudFront), but the F6 commit perpetuates and doubles down on the inconsistency in the new docstring (`pricing-enricher.ts:828–836`) that calls it a "display label, not a math conversion."

  This commit is the right place to either: (a) add `scale: 10_000` to the four PER_10K_REQS decomposers so the display string becomes correct ($0.01/10K reqs) and update the F6 promotion path to divide back out (`perRequestRate = scaledRate / scale`); or (b) drop the `PER_10K_REQS` unit entirely and use `/req` everywhere, which makes the display unambiguous at the cost of less-friendly labels for low-cost services. Either way: the comment "The decomposer's `priceUnit: '/10K reqs'` is a DISPLAY label, not a math conversion" institutionalizes a bug.

### MED (should address in follow-up)

- **Stale `/10_000` claim in test fixture docstring** (`pricing-enricher.test.ts:961–964`). The block comment above `CLOUDFRONT_REQUESTS_RESPONSE` says:

  > "The pricing-enricher converts it into a per-request rate (rate / 10_000) so multiplication with raw request counts is straightforward."
  > Production code does NO `/10_000` conversion (verified — the regex at `pricing-enricher.ts:837` only strips `$` prefix and `/<unit>` suffix). This is the residual self-flagged artifact (concern #3) — caught by the author during development, fixed in code, comment left behind. Future readers will misread the fixture intent. Two-line fix: replace with "The pricing-enricher uses the raw rate (per-1-request) directly — `priceUnit: '/10K reqs'` is a display label only."

- **No IAM policy regression test for the namespace condition** (`packages/core/src/config/iam-policies/operator.ts:235`). The widening from `"cloudwatch:namespace": "AWS/S3"` (single string) to `"cloudwatch:namespace": ["AWS/S3", "AWS/CloudFront"]` (array) is the kind of change a snapshot test should lock down. Grep on the codebase shows ZERO references to `CloudWatchStorageMetricsRead` outside `operator.ts` itself — there's no test that asserts the Condition shape, so a future regression that drops one namespace (or reverts to the string form, which IS a different IAM evaluation path) wouldn't be caught. Recommendation: add a unit test in the operator-policy suite that asserts `cloudwatch:namespace` is an array containing exactly `["AWS/S3", "AWS/CloudFront"]`. Tracker rationale: M instead of HIGH because the only consumer of this policy is the CloudWatch enricher itself, and the enricher's behavioral test would catch a real production regression — but only via integration, not unit-level.

- **No CloudFront-side multi-edge-region test fixture** (`pricing-enricher.test.ts:910–960`). The `CLOUDFRONT_DATA_TRANSFER_TIERED_RESPONSE` fixture has exactly ONE product entry (North America). Real `AmazonCloudFront` `productFamily=Data Transfer` responses return ~10 entries, one per edge region. The current test never exercises the "MCP returns multiple matching items and we pick the first one" code path — which is the very path that produces the non-deterministic rate selection flagged in HIGH-1. Recommendation: add a test fixture with 3+ edge-region entries (NA at $0.085, JP at $0.114, SG at $0.120 say) and assert which one is picked + what $/mo result the test gets — so the fix for HIGH-1 above has a regression-protection harness.

- **No 3-tier-crossing test** for `computeTieredCost`. Current tests cover tier-1-only (1000 GB) and tier-crossing-1-to-2 (15360 GB). A 60 TB volume (61440 GB) would span all three tiers (tier 1: 10240 × $0.085 = $870.40, tier 2: 40960 × $0.080 = $3276.80, tier 3: 10240 × $0.060 = $614.40, total $4761.60) and lock in the bottom-tier branch behavior. Low effort; high regression-protection value for a math helper.

- **No regression test asserting PriceClass_100 vs PriceClass_All produce the same $/mo today** (documenting the deferred behavior). If/when a future change adds PriceClass-aware pricing, there's no test that flips from "they're the same today (limitation)" to "they're different (feature)" — meaning the limitation could be silently fixed AND silently broken in the same change. Recommendation: add a comment-only `it.todo("PriceClass-aware pricing — currently uses PriceClass_All for all distributions")` so the gap is at least visible in the test runner output.

- **No partial-success CloudWatch test** (Requests succeeds, BytesDownloaded fails or vice versa). Test at `storage-enricher.test.ts:521-538` covers "BytesDownloaded throws → whole resource dropped," but does NOT cover "BytesDownloaded returns empty datapoints while Requests has data" — which the enricher would treat as bytes=0, requests=N, then the pricing-enricher's `bytesGb > 0` guard falls back to rate hint. That's the correct behavior but worth locking with a test.
