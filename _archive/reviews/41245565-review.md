## External-Claim Verification — turbo `--continue` Exit Code

Two-channel verification, both producing the same answer.

### Channel 1 — `turbo --help` (definitional)

Local turbo 2.8.17 (the version invoked via `npx` in CI) help output for `turbo run`:

```
--continue[=<CONTINUE>]
    Specify how task execution should proceed when an error occurs.
    Use "never" to cancel all tasks.
    Use "dependencies-successful" to continue running tasks whose dependencies have succeeded.
    Use "always" to continue running all tasks, even those whose dependencies have failed
    [default: never]
    [possible values: never, dependencies-successful, always]
```

The flag affects **scheduling**, not the final exit status. Nothing in the help text suggests `--continue` suppresses the aggregate failure exit code. With no value, `--continue` means `dependencies-successful`.

### Channel 2 — empirical repro (operational)

Spun up a throwaway pnpm workspace at `/tmp/turbo-continue-test/` with two packages: `pkg-a` (`"test": "exit 1"`) and `pkg-b` (`"test": "echo b-ok"`). Both at the same topological level, no inter-package deps (matching the assignee.ai layout — `test:coverage` has `"dependsOn": []` in `turbo.json`).

Direct turbo binary invocation (bypassing shells/wrappers):

| Invocation                      | Exit code |
| ------------------------------- | --------- |
| `turbo run test` (default)      | **1**     |
| `turbo run test --continue`     | **1**     |
| `npx turbo run test --continue` | **1**     |

Turbo's own stderr in the `--continue` run prints both `pkg-a#test: command exited (1)` and `ERROR run failed: command exited (1)`, then exits 1. `pkg-b` still ran to completion (verified by stdout `b-ok`), which is the desired enumeration behaviour. **Exit-code semantics are preserved.**

(Brief footnote: an earlier pass observed `EXIT_CODE=0` — that was a `tail -25` consuming the pipeline status; rechecking with `>/dev/null 2>&1; echo $?` shows the real `1`. Worth flagging because anyone re-verifying this locally needs to avoid the same pipe trap.)

## Findings

### LOW-1 — Comment slightly overstates parallel behaviour

`ci-core.yml:175-180` says vitest "reports all failures within a file/package, but turbo masks failures in packages it never reaches." That's correct for the default `--continue=never`, but technically turbo doesn't "stop scheduling" — it cancels in-flight tasks of unstarted packages. Functional outcome is identical (failures stay hidden), so the rationale lands. Not blocking; just imprecise.

**Fix (optional, follow-up):** s/"turbo stops scheduling"/"turbo cancels remaining tasks"/. Skip if the comment was deliberately simplified.

### LOW-2 — `turbo.json` `test:coverage.dependsOn = []` makes `--continue` and `--continue=always` identical here

Since no `test:coverage` task depends on another package's `test:coverage`, the default-`dependencies-successful` semantics never apply (no upstream task can have failed-dependencies). If a future refactor introduces cross-package deps (e.g. integration coverage that consumes another package's coverage report), the current bare `--continue` would skip the dependent task on a failed upstream — which may not be what the windows-enumeration backlog actually wants. Today: no impact.

**Recommendation:** if you want to be explicit that "enumerate everything, always", consider `--continue=always`. For now, bare `--continue` is correct and the more conservative choice. No change required.
