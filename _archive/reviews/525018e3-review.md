## Vitest claim verification

- `vitest@3.2.4` installed (`node_modules/vitest/package.json`).
- Confirmed `"forks"` is a valid `BuiltinPool` literal:
  `node_modules/vitest/dist/chunks/reporters.d.BFLkQcL6.d.ts:`
  `type BuiltinPool = "browser" | "threads" | "forks" | "vmThreads" | "vmForks" | "typescript"`.
- Ternary `process.platform === "win32" ? "forks" : "threads"` —
  `"win32"` is Node's canonical Windows token; POSIX (linux/darwin)
  falls through to `"threads"`, which IS the prior default. Zero
  behaviour change on macOS / Linux runners.

## Findings

1. **All 4 configs structurally identical** — `git diff --stat`
   reports 4 files × 7 insertions = 28 (matches spec exactly). The
   pool line lands inside `test:` block, after `retry: 1`, before
   `coverage` / `maxConcurrency` — no scope confusion. (apps/cli L25,
   apps/mcp-server L24, packages/best-practices L24, packages/core L81.)
2. **No orphaned thread-specific keys** — grep for `poolOptions`,
   `isolate`, `fileParallelism` in the 4 configs returned empty. No
   `poolOptions.threads` will silently no-op under forks.
3. **No prior `pool:` setting** — only the new line matches
   `^\s*pool\s*:` in the 4 files. No duplicate / override risk.
4. **Coverage interaction unchanged on POSIX** — POSIX branch
   evaluates to `"threads"` (the prior implicit default), so v8
   coverage runs unchanged. Coordinator macOS run on best-practices
   (994/994) corroborates.
5. **Forks cost on Windows** — child_process spawn adds ~per-worker
   startup overhead vs. worker_threads. Acceptable trade-off: the
   alternative is red CI. Worth monitoring Windows job wall-time post-
   merge; if >+30s per package, consider `poolOptions.forks.singleFork`
   tuning in a follow-up.
6. **No YAML / no `--continue` interaction** — turbo flag is task-
   level, vitest pool is process-level, orthogonal.
